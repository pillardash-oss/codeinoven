CodeInOven / header study
Recommendation
Seven variants · one bar

The header has to survive four different windows.

macOS draws three lights inside the left edge. Windows overlays three caption buttons on the right. A Linux desktop can do either, and some distributions flip it per user. Everything else in the bar is ours, and it has to look deliberate in all four cases.

What the study fixes The OS zones never move, so the design job is deciding what of ours sits next to them. Seven answers below, each drawn on macOS, Windows and a narrow window. The detail screens add both Linux directions.

V1 · Reserved edge

closest to today

The bar keeps two fixed gutters and a hairline seam where each one ends. Our controls sit strictly inside the remaining width, with a 4px floor before any seam. Predictable, and the seam makes the reserved space read as intentional rather than as padding nobody accounted for.

All four platforms

V2 · Split centre

edge-independent

Thread actions stop anchoring to a window edge and ride at the end of the centred band. Measure from the middle of the bar and the cluster lands in the same visual place whether the lights are left or the captions are right. Only the bell and the notes button touch an edge, and only the edge the OS has left free.

All four platforms

V3 · The rail owns the actions

fewest moving parts

Spec, git, notes and the view's quick actions move to the left rail, which the OS never touches. The bar keeps identity, the thread title, and the bell. Nothing can collide because nothing is left to collide with.

All four platforms

V4 · Command field

shell-like

One field in the middle. Thread state and the right-hand actions become chips inside it, so the bar holds three controls no matter how much the thread needs. The field is centred, so it is the one element that looks identical on every platform.

All four platforms

V5 · Two tiers

costs 32px of height

The 48px drag row belongs to the window: OS zone, identity, title, bell. A 32px strip below belongs to the app: view actions left, thread actions right, full width. The OS never shares a row with an app action, at the price of a taller chrome.

All four platforms

V6 · Priority ladder

fixed slot count

Three slots, filled in priority order: the view's actions, then the thread's, then the global pair. Everything else goes to one overflow menu that opens away from the OS zone. Labels ride along while there is room and drop before the icons do.

All four platforms

V7 · Fixed spine

one column, left-aligned

A fixed-width column holds identity, back and forward, and the view's actions, with a hairline between each group. The thread title follows the column, aligned left. The column's width does not depend on the title, so the title always starts on the same pixel, and the bar reads from one edge instead of from the middle.

Both gutters, all four platforms
